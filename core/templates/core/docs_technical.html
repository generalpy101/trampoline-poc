Technical

Service shape, data model, caching, and the operational details that turn the algorithm into a working system.

Service shape

A single Django app, core, exposes one JSON endpoint that the storefront calls per product view: 

GET /api/estimate?sku=<product_id>&pincode=<pincode>

Response:
{
  "earliest_date":          "2026-06-10",
  "latest_date":            "2026-06-10",
  "is_range":               false,
  "confidence":             "high",
  "tier":                   "in_stock_nearest",
  "tier_label":             "In stock nearby",
  "reason":                 "In stock at our Delhi warehouse",
  "warehouse_code":         "WH-DEL",
  "total_days_from_today":  4,
  "breakdown":              [ ... ],
  "serviceable":            true,
  "served_from_cache":      false
}

Two helper endpoints support the demo interface (/api/inventory/<sku> and POST endpoints to mutate stock); production deployments would protect those with auth.

Data sources

SourceWhat it gives usRefresh
Warehouse system Live stock per (product, warehouse) Real-time, read at request time
Production / supplier system Pending batches with promised date, quantity, and supplier ID Real-time, read at request time
Order management Completed deliveries: shipped_at, delivered_at, lane, carrier Daily aggregation into pre-computed per-lane percentiles

The first two sources are read live (and cheap — they're indexed lookups). The third feeds the pre-aggregated LanePerformance table; the estimator never queries raw delivery history at request time.

Data model

TableHolds
WarehouseWarehouses with their region (north / west / south / east)
ProductSKU, name, category, weight class, supplier
SupplierProduction suppliers
PincodeClusterDelivery zones (~2k in production)
PincodeMappingPincode → cluster lookup table
InventoryCurrent stock per (product, warehouse)
ProductionBatchScheduled, in-transit, and received batches
DeliveryRecordEvery completed shipment — the history we learn from
LanePerformancePer-lane P50/P80/P95 transit (refreshed nightly)
SupplierReliabilityPer-supplier P50/P80 slip days against promised batch date
PredictionShadow log of every estimate served, later joined to actual outcome

Eleven tables, three of which (LanePerformance, SupplierReliability, Prediction) are derived from the others. The first eight model the operational domain; the derived three are what makes the algorithm cheap to evaluate at request time.

The entry point

The whole tier dispatch fits in 15 lines:

def compute_estimate(product, pincode):
    today = timezone.localdate()
    handling = settings.HANDLING_BUFFER_DAYS

    cluster, match_quality = resolve_cluster(pincode)
    if cluster is None:
        return _not_serviceable(today, pincode)

    stocked = list(
        Inventory.objects.select_related("warehouse")
            .filter(product=product, quantity__gt=0)
    )

    if stocked:
        return _estimate_in_stock(today, handling, stocked, cluster, match_quality)

    return _estimate_out_of_stock(today, handling, product, cluster, match_quality)

Every branch returns the same response shape — date, confidence, reason, breakdown — so the front end never needs to know which tier answered. Two helper functions (_estimate_in_stock and _estimate_out_of_stock) contain the actual math; both are small enough to read in 30 seconds.

Caching

Responses cache for 15 minutes via Django's cache framework. The cache key includes more than just the obvious inputs: 

cache_key = (sku, cluster, match_quality, percentile)

The match_quality component matters because exact-pincode matches and prefix-pincode matches produce different confidence levels and reason text, so they must not share a cache entry. The percentile component lets you change DELIVERY_PROMISE_PERCENTILE in settings and immediately stop serving stale entries computed under the old value.

Invalidation triggers on inventory threshold crossings (in-to-out, below-safety) rather than every single quantity tick. Going from 50 units to 49 doesn't change the customer-facing date; going from 1 to 0 does. Filtering at the source keeps recompute volume bounded by meaningful state changes, not by order volume.

SQLite in production

SQLite is the production database. At this scale (thousands of page views per day, not millions), it's a deliberate choice: no separate DB server to operate, no network round-trip on every read, and the whole database can be backed up with a single file copy.

A connection signal in core/apps.py enables WAL mode and tunes the busy timeout on every new database connection: 

PRAGMA journal_mode = WAL;       -- readers proceed during writes
PRAGMA synchronous  = NORMAL;    -- durable across app crashes
PRAGMA busy_timeout = 5000;      -- wait 5s if the writer is busy
PRAGMA foreign_keys = ON;        -- enforce referential integrity

With these settings, SQLite comfortably handles the read/write patterns of a small Django service. Migrating to Postgres later is a one-line change in DATABASES.

Observability

Every prediction served is shadow-logged to the Prediction table with its inputs, the tier that fired, the date returned, and the confidence level. When the corresponding order eventually delivers, an actual_delivered_at column gets populated and a miss_days column is computed.

The Dashboard exposes two signals that tell us if the system is working:

  • On-time rate — should sit near the configured percentile (80%). A persistent drift below 75% indicates carrier or warehouse problems rather than a system bug.
  • Tier distribution — how often each branch fires. Sudden shifts are leading indicators of operational health: a spike in "Awaiting batch" means warehouses are running short; a drop in "In stock nearby" means a regional warehouse is struggling.

Where AI fits

Use AI for

  • Parsing unstructured supplier emails and PDFs about batch delays into structured arrival dates that feed the ProductionBatch table.
  • Generating the customer-facing reason copy so it reads naturally for any combination of inputs.
  • Drafting customer-support replies that reference the cached estimate.

Don't use AI for

  • The date prediction itself. It's a commitment shown at checkout — structured math is faster, cheaper, and more debuggable than a model that can hallucinate.
  • Cache invalidation. It's mechanical.
  • The tier routing. Deterministic if-else is the right tool.

Scaling roadmap

The architecture deliberately stops short of several capabilities that would be premature at this scale. The order they'd be added as traffic and data complexity grew:

  1. Precomputed hot-set. Identify the top product × cluster combinations from traffic data, keep them precomputed and refreshed proactively. The cold tail still computes on demand.
  2. Event-driven cache invalidation. Emit events when inventory crosses meaningful thresholds and recompute affected entries immediately instead of waiting for the TTL.
  3. Multi-carrier dimension. Track statistics per (warehouse, cluster, carrier) instead of just (warehouse, cluster). Pick the right carrier per request based on lane performance and cost.
  4. Learned model. Replace per-bucket percentile lookups with a quantile regression model. Earns its keep once the bucket-based approach plateaus on accuracy — typically when long-tail lanes have too few samples to be reliable.

None are worth building yet. The dashboard would tell us when they are: a sustained on-time rate gap, a precomputation cache hit rate that's lower than projected, or specific lanes whose accuracy lags the rest.
